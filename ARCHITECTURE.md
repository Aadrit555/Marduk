# MARDUK Architecture Specification

## 1. System Philosophy and Design Goals

MARDUK is an independent, Rust-first inference infrastructure and GPU orchestration platform designed for production environments. Its primary design objectives are:

1. **Deterministic Foundations First**: An explainable, robust mathematical baseline scheduler takes precedence before applying learned models.
2. **Honest Observability**: Hardware telemetry must accurately reflect physical device state via NVML. Missing metrics are marked unavailable, never populated with fabricated values.
3. **Strict Resource Isolation**: Memory headroom and worker health are enforced as hard constraints to eliminate out-of-memory crashes and cascading pipeline failures.
4. **Zero Hidden Runtimes**: Core orchestration, scheduling, and API management are implemented entirely in native Rust without a Python runtime dependency.
5. **Separation of Host Coordination vs. GPU Compute**: Efficient asynchronous channels (`tokio::sync::mpsc`), bounded queues, and zero unnecessary host-to-device buffer copying.

## 2. Workspace and Component Structure

MARDUK is organized as a Cargo workspace with distinct, decoupled crates:

```
marduk/
├── Cargo.toml                  # Workspace manifest
├── crates/
│   ├── marduk-core/            # Domain models, configuration, errors, metrics primitives
│   ├── marduk-nvml/            # Real NVML GPU discovery & telemetry polling engine
│   ├── marduk-worker/          # Worker lifecycle supervisor, process spawn & backend adapters
│   ├── marduk-scheduler/       # Constraint filter, cost scoring, backpressure, decision logs
│   ├── marduk-learned/         # Burn-based neural workload predictor & trace training
│   ├── marduk-api/             # Axum HTTP routes, SSE streaming, OpenAI compatibility
│   ├── marduk-bench/           # Reproducible benchmark harness (TTFT, ITL, latency, RPS)
│   └── marduk-cli/             # Main binary CLI (`marduk serve`, `marduk gpus`, etc.)
├── dashboard/                  # React + TypeScript observability dashboard
├── config/                     # Configuration templates
└── tests/                      # Integration and stress test suites
```

## 3. Component Details

### 3.1 Control Plane (`marduk-core`, `marduk-api`)

- **Configuration Engine**: Strongly typed TOML/YAML configuration parsed with Serde, supporting environment variable overrides.
- **Model Registry**: Catalogs registered models, parameter sizes, architecture types, context lengths, default precision (e.g. FP16, BF16, INT8, AWQ, GGUF), and estimated memory footprints.
- **Unified API**: Axum-powered HTTP service providing OpenAI endpoints (`/v1/chat/completions`, `/v1/models`) and an operations suite (`/api/v1/*`). Employs Tower middleware for timeout handling, CORS, rate limiting, and request tracing.

### 3.2 GPU Resource Manager (`marduk-nvml`)

- **Discovery**: Automatically scans PCIe bus IDs, detects all installed NVIDIA GPUs, extracts device names, UUIDs, architecture compute capabilities, and driver/CUDA versions.
- **Telemetry Loop**: Periodically polls devices (configurable 100ms - 1s intervals):
  - Memory: Total, Free, Used (bytes).
  - Utilization: GPU compute core %, Memory controller %, Video decoder/encoder %.
  - Thermals: GPU core temperature (°C), slowdown temperature limit.
  - Power: Instantaneous power draw (mW), power limit (mW).
  - Clocks: Graphics clock (MHz), Memory clock (MHz).
  - PCIe: PCIe throughput RX/TX (KB/s).
- **Fallback Behavior**: On systems lacking an active NVML driver or NVIDIA hardware, the telemetry layer reports host CPU and RAM metrics via `sysinfo` while clearly marking GPU metrics as unavailable.

### 3.3 Worker Manager (`marduk-worker`)

- **Worker Model**: A worker encapsulates an isolated inference engine instance (e.g. `mistral.rs` running in process or as a supervised child process).
- **Process Isolation**: Each worker child process can be constrained to specific GPU devices via `CUDA_VISIBLE_DEVICES` or device indices.
- **Lifecycle & Health**:
  - State machine: `Uninitialized` -> `Starting` -> `Healthy` -> `Busy` -> `Degraded` -> `Terminating` -> `Stopped`.
  - Heartbeat monitor detects non-responsive workers within a configurable threshold (e.g. 5 seconds) and triggers auto-restart or graceful rerouting.
- **Communication Protocol**:
  - High-throughput asynchronous channels with bounded buffers.
  - SSE streaming token translation: tokens generated by backend engines are streamed directly to the client without buffering full responses into host memory.

### 3.4 Intelligent Scheduler (`marduk-scheduler`)

The scheduling engine maps incoming `InferenceRequest`s to the optimal available worker:

#### Phase A: Hard Constraints (Admission & Eligibility)
A worker $W_i$ is discarded if any of the following fail:
1. $\text{Status}(W_i) \neq \text{Healthy}$
2. $\text{LoadedModel}(W_i) \neq \text{RequestedModel}$ and dynamically reloading model is disabled or infeasible.
3. $\text{QueueDepth}(W_i) \ge \text{MaxQueueCapacity}(W_i)$ (Backpressure constraint).
4. $\text{FreeVRAM}(\text{GPU}(W_i)) < \text{MinRequiredVRAM}(\text{Model}) + \text{KVBudget}(\text{Tokens})$.

If no worker passes Phase A, the request is immediately rejected with HTTP 429 (Too Many Requests / Capacity Saturated) or HTTP 503 (Service Unavailable), accompanied by a `Retry-After` header.

#### Phase B: Multi-Factor Scoring
For each eligible candidate $W_i$, an explainable cost score $S(W_i)$ is computed:

$$S(W_i) = w_{\text{queue}} \cdot T_{\text{wait}}(W_i) + w_{\text{exec}} \cdot \hat{T}_{\text{exec}}(W_i) + w_{\text{mem}} \cdot P_{\text{mem}}(W_i) + w_{\text{aff}} \cdot C_{\text{reload}}(W_i)$$

Where:
- $T_{\text{wait}}(W_i) = \text{QueueDepth}(W_i) \times \bar{T}_{\text{service}}$: Estimated queue waiting time.
- $\hat{T}_{\text{exec}}(W_i)$: Estimated computation time based on prompt length and `max_tokens`.
- $P_{\text{mem}}(W_i) = \left( \frac{\text{UsedVRAM}}{\text{TotalVRAM}} \right)^2$: Quadratic memory pressure penalty to penalize over-allocating nearly full VRAM.
- $C_{\text{reload}}(W_i)$: Severe cost penalty applied if the worker must unload its current model to load the requested model.

The candidate with the **lowest cost** is selected.

#### Phase C: Explainability & Audit Log
Every routing decision generates a structured audit record:
```json
{
  "request_id": "req-98f2b1",
  "model": "mistral-7b-instruct",
  "selected_worker": "worker-gpu0-01",
  "reason": "Lowest queue wait time (42ms) and model already resident in VRAM with 1.8GB headroom",
  "candidates_evaluated": [
    { "worker_id": "worker-gpu0-01", "score": 0.24, "queue_depth": 1, "free_vram_mb": 1840 },
    { "worker_id": "worker-gpu1-01", "score": 0.89, "queue_depth": 5, "free_vram_mb": 820 }
  ],
  "disqualified": [
    { "worker_id": "worker-gpu0-02", "reason": "Insufficient VRAM headroom (requires 2048MB, available 512MB)" }
  ]
}
```

## 4. Concurrency and Data Plane Performance

- **Async Core**: Implemented with Tokio multi-threaded runtime.
- **Lock-Free / Low-Contention State**: Shared state is encapsulated in `Arc<RwLock<T>>` or atomic primitives (`AtomicUsize`, `AtomicBool`) for metrics counters, ensuring zero lock contention in the hot request path.
- **Bounded Buffers**: All channels (`tokio::sync::mpsc::channel`) have explicit bounds to prevent memory bloat under sustained load spikes.
- **Cancellation Propagation**: If a client terminates an HTTP connection during token streaming, the downstream worker's generation loop receives a cancellation signal and frees the associated KV-cache context immediately.

## 5. Learned Scheduling Module (`marduk-learned`)

- **Design**: Serves as an auxiliary advisory model running alongside the deterministic scheduler.
- **Framework**: Implemented using the **Burn** deep learning framework with the `ndarray` CPU backend (and optional WGPU/CubeCL backend) to ensure clean cross-platform execution.
- **Prediction Targets**:
  - Time-to-first-token (Prefill latency).
  - Inter-token generation latency (Decode throughput).
  - Peak KV-cache memory requirement.
- **Shadow Mode**: In shadow mode, the neural predictor evaluates live traffic and logs recommendations alongside the deterministic scheduler's choices. Only when verified through offline trace evaluation and shadow mode benchmarks can learned routing take effect.
